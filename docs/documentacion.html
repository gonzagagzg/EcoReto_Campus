5. Tecnologías utilizadas

Backend (backend/)

  • Node.js 24 + npm 11
  • NestJS 12 + TypeScript 6
  • PostgreSQL 15+ + TypeORM 1 + pg
  • Auth JWT access + refresh (@nestjs/jwt, bcrypt)
  • class-validator / class-transformer
  • Subida local con Multer/Express (/uploads)
  • Tareas programadas (@nestjs/schedule)
  • Jest 30 + Supertest, oxlint, Prettier

Frontend (frontend/)

  • Angular 22 standalone + TypeScript 6
  • Capacitor 8 (core, android, ios, camera, filesystem, network)
  • RxJS 7, Angular Router, Forms
  • scripts/load-env.mjs genera environment.ts + public/config.json
  • Vitest 5 + jsdom, Prettier

Base de datos

  • PostgreSQL, script database/ScriptEcoRetoBD.sql
  • ENUMs: rol_enum, estado_reto_enum, estado_evaluacion_enum, categoria_reto_enum, etc.
  • Tablas: usuarios, retos, retos_participantes, participacion_reto, premios, gustos, soporte

7. Descripción de la arquitectura

Arquitectura general (cliente-servidor + móvil híbrido)

Navegador / App Capacitor (Angular 22)
      │  HTTP JSON + FormData (fotos)   /gg/* , /uploads/*
      ▼
API NestJS (:3000) ── TypeORM ──► PostgreSQL (ecoretobd)
      │  Multer ──► /backend/uploads (estáticos /uploads)
      │  JWT access (2h) + refresh (7d), CORS, cron nocturno
  • Backend modular por dominio: auth, usuarios, retos, participaciones, premios, gustos, soporte, supervisor, admin, tasks (backend/src/modules/). Cada módulo: controller → service → dao → entity + dto.
  • Prefijo global: app.setGlobalPrefix('gg') en main.ts; API en /gg, archivos en /uploads.
  • Configuración validada: ConfigModule.forRoot({ validate: validateEnv }) con env.validation.ts; DB_SYNCHRONIZE=false (el esquema lo manda el .sql).
  • Frontend en capas: views/ (páginas) → core/services/ (API) → core/models/ + shared/ (alerta, utils). Layout único MainLayoutComponent con header/sidebar.
  • Config dual: load-env.mjs genera environment.ts (respaldo compilado) y config.json (editable sin recompilar) con lista backends para failover.

10. Explicación de las validaciones

Backend (rechaza primero, con 400)

  • Global: ValidationPipe({ whitelist: true, forbidNonWhitelisted: true, transform: true }) en app.module.ts + validateEnv al arrancar.
  • DTOs con class-validator: ej. CrearRetoDto (@MinLength(3)/@MaxLength(150) nombre, @MinLength(10) descripción, @IsDate() fechaLímite); RegistroDto (@IsEmail(), contraseña @MinLength(8)/@MaxLength(72), cédula única, idsGustos enteros ≥1); CanjearPremioDto (@IsInt() @Min(1)).
  • Archivos: opcionesImagen (solo JPG/PNG/WebP, límite de tamaño) en todos los FileInterceptor('imagen').
  • Auth/autorización: JwtAuthGuard + RolesGuard + @Roles(...) en cada controlador; ParseIntPipe en :id.

Frontend (evita viajes inútiles)

  • Validación manual espejo del backend: ej. crear-reto.component.ts → enviar() (nombre ≥3, descripción ≥10, fecha > hoy, imagen debe ser image/*), registro (email institucional, clave ≥8).
  • Errores del servidor se muestran con AlertaComponent + mensajeDeError(err).

11. Explicación de las reglas de negocio

Fuente: backend/src/modules/retos/reglas-reto.ts y participaciones/services/progreso-puntos.service.ts (funciones puras + servicio único de progreso).

ReglaDetalle
DuraciónReto entre 5 y 300 días (DIAS_MINIMOS/MAXIMOS_RETO); vencimiento a finDelDia() (23:59:59.999).
Dificultad automática≤50 días = Fácil, ≤150 = Medio, >150 = Difícil. El cliente no la envía.
PuntosFácil: 5 pts c/5 días (tope 50). Medio: base 50 + 50 c/50 días extra (tope 150). Difícil: base 150 + 50 c/50 días (tope 300). Participar sin completar = 25% (PORCENTAJE_POR_PARTICIPAR).
Pago por evidenciasfactorPorEvidencias(aprobadas, requeridas): 0 sin aprobadas; 100% al completar (pago inmediato y cuenta como cumplido); incompleto solo liquida al cerrar: 25%/50%/75% por tramo.
NivelcalcularNivel(retosCumplidos): 0 con 1 cumplido, 1 con 2, 2 con 4… (potencias de 2) hasta nivel 100.
Saldopuntos = max(0, ganados − canjeados); nunca baja de 0 ni de lo ya canjeado.
Flujos de estadoReto: Pendiente_Aprobacion → Activo → Finalizado (o Negado/Bloqueado/Desactivado). Evidencia/soporte: Enviado → Aprobado/Negado/Bloqueado. Usuario: pendiente/activo/desactivo/bloqueado. Canje: pendiente → listo para reclamar → reclamado (o negado/bloqueado).
RolesUsuario < Supervisor < Administrador; crear reto lo puede cualquiera autenticado, aprobar solo staff.

14. Conclusiones

  • La gamificación (puntos proporcionales + niveles + ranking + premios) convierte acciones ambientales en un ciclo medible y motivador.
  • Calcular dificultad/puntos en el backend (reglas-reto.ts) evita trampas desde el cliente y unifica el criterio.
  • El servicio único de progreso (ProgresoPuntosService) garantiza que la revisión inmediata y el cron nocturno nunca diverjan.
  • La config runtime (config.json + failover) da resiliencia en demos con túneles y en despliegues sin recompilar.

15. Recomendaciones

  • Migrar uploads/ local a almacenamiento externo (S3 o similar) para producción y múltiples instancias.
  • Agregar notificaciones (push/email) al aprobar/negar evidencias y al vencer retos.
  • Ampliar e2e (auth, ciclo completo de reto, canje sin saldo) y subir cobertura de ProgresoPuntosService.
  • Endurecer producción: NODE_ENV=production, CORS_ORIGINS explícito, secretos largos rotados, DB_SYNCHRONIZE=false + migraciones versionadas.
  • Completar docs/capturas/ y un video corto del flujo estudiante → supervisor → premio.
